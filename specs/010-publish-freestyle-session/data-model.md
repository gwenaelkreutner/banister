# Phase 1 Data Model: Publish a Freestyle Session

## `freestyle_published_entries` (new table)

| Column | Type | Notes |
|---|---|---|
| `id` | UUID, PK | |
| `user_id` | UUID, FK → `users.id`, `ON DELETE CASCADE`, NOT NULL | single-user product, but kept explicit like every other table |
| `external_id` | string, NOT NULL, unique per user | `banister:freestyle:<yyyy-MM-dd>:<workout_type>-<id8>` (Research Decision 6) — same `banister:` prefix as `PublishedEntry` so both tables' entries are equally recognizable as "ours" on the calendar |
| `intervals_event_id` | string, NOT NULL | remote event id, required for a future delete |
| `session_date` | date, NOT NULL | the date it was published for |
| `workout_type` | string, NOT NULL | `"long_ride" \| "intervals" \| "endurance" \| "recovery"` — same vocabulary as everywhere else, no `week_number`/`day_of_week` (there is no plan position to record, Research Decision 4) |
| `content_hash` | string, NOT NULL | SHA-256 of what was actually rendered and written — the record that makes SC-002 checkable after the fact |
| `published_at` | timestamp, NOT NULL | |
| `withdrawn_at` | timestamp, nullable | mirrors `PublishedEntry.withdrawn_at` — kept as history, not deleted, for the same reason (US3: "we withdrew this" vs "never published" must stay distinguishable) |

No `plan_id`, no `approval_id` (Research Decision 4/5) — this table only ever holds freestyle-mode writes.

**Migration**: one Alembic revision, autogenerated. No SQLite `ALTER COLUMN` involved (new table, not an
altered one) — the batch-mode workaround spec 009 needed does not apply here.

## FSM data: pending freestyle suggestion (not a new DB entity)

Held in the athlete's FSM context data (`state.update_data(...)`), not the database — it is by definition
gone once resolved (published, superseded, or the conversation moves on), and nothing about the athlete's
history depends on remembering a suggestion they never confirmed.

| Field | Type | Purpose |
|---|---|---|
| `pending_freestyle_id` | str (short id) | what a tapped button's `callback_data` is compared against (Research Decision 3) |
| `pending_freestyle_suggestion` | dict | the exact `FreestyleSuggestion` fields (`workout_type`, `template_id`, `steps`, `duration_minutes`, `target_tss`, `zone_code`) needed to render and publish without recomputing — publishing must act on what was shown (SC-002), not a freshly recomputed session |

Overwritten (never appended) every time a new suggestion is shown — only one can be pending at a time
(spec's Assumptions).

## State transitions

```
[Athlete asks for a session, freestyle mode]
        │
        ▼
[Suggestion shown, with a "📅 Publier sur intervals.icu" button]
   pending_freestyle_id = X
        │
        ├── athlete asks for a different one ──► [New suggestion shown]
        │                                          pending_freestyle_id = Y (X's button now stale)
        │
        ├── athlete taps X's button, id still current ──► create_event() ──► freestyle_published_entries row
        │                                                                     pending cleared
        │
        ├── athlete taps X's button, id no longer current (Y is) ──► "no longer current" message, nothing written
        │
        └── conversation moves on, nothing tapped ──► pending data simply sits unused; harmless (no TTL needed —
                                                        a stale id can never match a later one, Decision 3)
```

## Relationship to spec 009 entities

- Consumes spec 009's `FreestyleSuggestion` (`app/engine/freestyle_selector.py`) unchanged — this feature
  never alters how a session is chosen, only what happens once the athlete accepts one.
- `app/bot/routers/goal.py::_regenerate()` (freestyle → goal mode, spec 009) gains one more withdrawal call
  alongside the existing plan-entry withdrawal path, this time over `freestyle_published_entries` (FR-011).
